# cpu_65c02 vs R65Cx2 — cycle-level comparison of the r65 stimulus pair

Date: 2026-09 (analysis of traces generated by `run_divergence.ps1`)
Scope: the **r65c02 stimulus pair** — new core `rtl/new_cpu/cpu_65c02.sv`
versus the Verilog golden `rtl/R65Cx2.sv` under the shared 64K r65 image.

Verdict up front: **the two cores are functionally equivalent on this
stimulus.** Instruction stream, all memory writes (final RAM), interrupt
stack bytes, and end-state registers all match. The only real differences
are per-instruction cycle counts on **four opcodes** (six instances), plus a
cosmetic difference in how the (non-existent) B flag is displayed. Details,
methodology, and the decision this leaves for the project are below.

## 1. Inputs

| Item | Golden (G) | New core (N) |
|---|---|---|
| Module | `rtl/R65Cx2.sv` (`R65C02`, FPGA64/A.Daly lineage) | `rtl/new_cpu/cpu_65c02.sv` (+ `cpu_alu.sv`) |
| Testbench | `module_tests/r65c02/r65c02_verilog_tb.sv` | `module_tests/cpu_65c02/cpu65_r65_tb.sv` |
| Trace | `module_tests/r65c02/build/verilog_trace.csv` | `module_tests/cpu_65c02/build/r65_trace.csv` |
| Length | 4000 cycles, 22 columns (identical header) | same |

Both testbenches load the **same** 64K image
(`module_tests/r65c02/build/r65_mem_init.hex`, generated by
`build/gen_mem_array.pl` + `program_table.pl`) and apply the same stimulus:
directed program at `$0500` (~324 instructions, all addressing modes, full
stack set, taken/not-taken branches, JSR/RTS, indirect JMPs, NOP sleds) with
an **IRQ pulse at cycle 730** (handler `$1020`) and an **NMI pulse at
cycle 768** (handler `$1030`); handlers return via explicit JMP, so the
trace ends with both interrupts still active (SP = `$F7`).

Lineage note: `R65Cx2.sv` has itself been proven equivalent to the VHDL
golden (`Apple-II_MiSTer_newsdee/rtl/R65Cx2.vhd`) by
`module_tests/r65c02/run_equivalence.ps1` (all fields compared, `P_B`
skipped because it is never driven in VHDL). Comparing N against the Verilog
golden is therefore a valid link in that chain.

Trace columns:
`CYCLE,PC,SP,P_N,P_V,P_R,P_B,P_D,P_I,P_Z,P_C,Y,X,A,ADDR,DI,DO,RW,NMI_N,IRQ_N,SYNC,SYNC_IRQ`

## 2. Methodology

Row-aligned field comparison is **not sufficient** for this pair: the cores
have different pipeline phase conventions and (as it turned out) different
cycle counts on a few opcodes, so rows drift apart in content. The analysis
therefore proceeds in six steps, each discarding or explaining a class of
apparent difference before moving to the next.

### Step 1 — raw row-aligned census, then reclassification

A naive field-by-field diff of the two CSVs reports thousands of differences;
almost all are sampling artifacts (Section 3). Each differing row is
classified:

- `ADDR` or `DI` differs → candidate real difference (or phase drift, see Step 2)
- only `RW` differs, with `ADDR`+`DI`+`DO` equal → **write-cycle sampling
  edge** (artifact): the two cores put the write strobe on different edges of
  the same bus cycle
- `DO` differs while `RW=1` → **stale output data** (artifact): `DO` is only
  meaningful on write rows (`RW=0`)

Result in the in-phase region (reset through G cycle 542, before any
cycle-count divergence): `ADDR` and `DI` are identical on **every** row; the
only row-level differences are 16 RW-only flips. Across the full trace there
are 12 rows where `ADDR`+`DI`+`DO` all match but only `RW` differs.

### Step 2 — instruction alignment by fetch events

Instruction *i* in G is aligned with instruction *i* in N by pairing the
*i*-th `SYNC=1` row (opcode fetch) in each trace and comparing the fetch's
`ADDR` and `DI` (the opcode byte). This is robust because:

- The **`PC` column must not be used** for alignment: G's `PC` lags by one
  row on the first fetch after reset and after taken branches, and N's
  register columns update one row earlier than G's. Fetch `ADDR` on
  `SYNC=1` rows is unambiguous in both traces.
- If the instruction streams ever diverged (wrong opcode executed), the
  pairing would show an opcode/address mismatch at that point.

Result: **1504 fetch events in each trace, 1504/1504 aligned pairs, zero
opcode/address mismatches.** The cores execute exactly the same program.

### Step 3 — per-instruction cycle-count diff

For each aligned pair *i*, instruction length = (fetch cycle of *i+1*) −
(fetch cycle of *i*). Lengths are bucketed by opcode + addressing mode
(decoded with the classic 6502 encoding table used by the r65 harness).

Result: every opcode/mode class has identical G/N lengths **except four
opcodes** (Section 4.1). Cumulative delta (G − N fetch cycle) walks
0 → +1 → +2 → +3 → +4 across the four `.ax` shift instructions at `$0672`–
`$067B`, then back to +2 after the two indirect JMPs at `$06C0`/`$06CA`, and
stays +2 to the end of the trace (last aligned fetch: G cycle 3999, N cycle
3997, both at `$0908`).

### Step 4 — state comparison at instruction boundaries, with update-skew tolerance

Registers/flags are compared on the **last row of each aligned instruction**
in each trace. Because G's state columns settle one row later than N's, a
difference at that sample point is not trusted until it is checked against
the raw rows: dump both cores' rows for the instruction (and its neighbors)
and verify whether the "difference" is just the ±1-row update skew. Every
apparent SP/Z/N/C/I boundary difference found this way turned out to be
update skew — e.g. after `PHA @ $05A9` both cores write `5A → $01FD` and
SP→`FC` on the same row, sampled one row apart; after `TSB $80 @ $0640` both
end with Z=1.

### Step 5 — global memory reconstruction

Independently of cycle alignment, replay **every write transaction**
(`RW=0` rows: `ADDR ← DO`) in each trace into a 64K array and diff the two
final images. This is phase-insensitive: it catches any real data divergence
anywhere in the trace regardless of the ±2-cycle drift.

Result: **33 addresses written in each trace; final values identical at all
33.** (Includes the `$0A00`/`$0A78` shift targets, all stack writes, and the
interrupt pushes.)

### Step 6 — HDL cross-check of every surviving difference

Each real difference from Steps 3–5 is located in both sources so the report
states *why* it exists, not just *that* it does:

- G: `rtl/R65Cx2.sv` (state machine + opcode table; B-flag comment block at
  ~line 655, `aluModeP` push composition)
- N: `rtl/new_cpu/cpu_65c02.sv` (`reg_p` definition, `int_active`,
  `do_writeback(R_P)`, and the `S_ABS_HI`/`S_IDX_FIX`/`S_READ`/`S_RMW_M`
  timing paths)

## 3. Trace artifacts (must be excluded before interpreting any diff)

| Artifact | Rule |
|---|---|
| `DO` on read rows is stale or actively driven | Ignore `DO` whenever `RW=1` |
| Write-strobe phase differs between cores | Rows with equal `ADDR`+`DI`+`DO` but flipped `RW` are the same bus event, not a difference |
| G's `PC` column lags one row after reset / taken branches | Never align on `PC`; use fetch `ADDR` on `SYNC=1` rows |
| N's state columns settle one row earlier than G's | Compare state at instruction boundaries; verify any boundary diff against raw rows before calling it real (±1-row skew) |
| After the first cycle-count divergence (G cyc 542), rows are phase-drifted by 1–2 cycles | Any row-aligned comparison beyond that point is meaningless; use Steps 2, 3, 5 instead |

## 4. Results

### 4.1 Cycle-count differences — the only real behavioral delta

Four opcodes, six instances in this trace (one instance each of the four
shift/rotate `.ax` forms plus two indirect JMPs):

| Opcode (instances) | G cycles | N cycles | G bus pattern | N bus pattern | Real silicon |
|---|---|---|---|---|---|
| ASL abs,X `$1E` @0672, ROL `$3E` @0675, LSR `$5E` @0678, ROR `$7E` @067B (target `$0A78`) | **7** | **6** | fetch×3, R, R, **W(old)**, W(new) | fetch×3, R, R, W(new) | 6502: 5 (R,W); 65C02S: 6 (R,R,W) → N matches W65C02S |
| JMP (indirect) `$6C` @06C0 (ptr `$00F0`) | **5** | **6** | fetch×3, R lo, R hi | fetch×3, R lo, **R lo (again)**, R hi | 6502: 5 no-wrap; 65C02S: fixed 6 → each matches one |
| JMP (abs,X) `$7C` @06CA (ptr `$00E8`, X=0) | **5** | **6** | fetch×3, R lo, R hi | fetch×3, **R next-opcode ($06CD)**, R lo, R hi | 6502 and 65C02S: 6 → G is short one here |

Concrete example (ASL abs,X, target `$0A78`, old value `5B`, new value `B6`):

```
G (7 cycles)                          N (6 cycles)
c542 R $0672 1e   SYNC                c542 R $0672 1e   SYNC
c543 R $0673 00                              c543 R $0673 00
c544 R $0674 0a                              c544 R $0674 0a
c545 R $0A78 (DI=5b)                        c545 R $0A78 (DI=5b)
c546 R $0A78 (DI=5b)                        c546 R $0A78 (DI=5b)   ; 65C02 second read
c547 W $0A78 DO=5b   <- extra write of OLD c547 W $0A78 DO=b6
c548 W $0A78 DO=b6
```

Hardware-observable consequences: G emits an **extra real write strobe** on
the shift/rotate abs,X targets (carrying the pre-shift value — harmless to
RAM, visible as a WE pulse), N emits an **extra read strobe** on the pointer
low byte for JMP (indirect), and N reads the following opcode byte during
JMP (abs,X). Final memory is unaffected in all cases (verified in Step 5).

Everything else matches in cycle count — verified per instance for the
branch family (not-taken = 2, taken = 3, page-crossing taken BRA = 4, which
matches real silicon exactly in both models). The classes where *both*
models deviate from a 6502 in the same way: plain-abs RMW = 6 (6502: 5;
consistent with the 65C02's extra pre-write read that N implements
explicitly in `S_RMW_M`), and INC/DEC abs,X = 7 (6502: 6). JSR/RTS = 6 and
PHA/PLA = 3/4 match real silicon, as do all zp/zp,X/zp,Y/abs/abs,X/abs,Y
load-store forms.

### 4.2 Instruction stream

1504/1504 aligned fetch pairs identical (opcode + address). No wrong
instruction was ever executed by either core.

### 4.3 Memory and end state

- Final RAM image: **identical** at all 33 written addresses (Step 5).
- End-of-trace registers: PC, SP, A, X, Y and flags N,V,D,I,Z,C all equal in
  both cores (both sit in the final self-`JMP $0908` park loop, SP=`$F7`,
  I=1 — the handlers returned via explicit JMP long before cycle 4000).
  Only `P_B` differs — see 4.4.

### 4.4 Interrupts and the B flag

IRQ@730 and NMI@768 are handled identically: same stack bytes pushed
(IRQ: `06 E3 E0`; NMI: `07 01 64`), same vectors read (`$FFFC/D → $1020`,
`$FFFA/B → $1030`), same SP trajectory (`FD→FA→F7`).

The live `P_B` column differs throughout (G=0, N=1) but this is **cosmetic**:

- G has no B register. Its documented model (`R65Cx2.sv` ~line 655): "No
  actual 'B' flag exists inside the 6502's processor status register. The B
  flag only exists in the status flag byte pushed to the stack… when the
  flags are restored (via PLP or RTI), the B bit is discarded." Pushed B =
  `~irqActive` → **1 for PHP/BRK, 0 for IRQ/NMI** (`aluModeP`).
- N also has no B register. `reg_p = {fl_n, fl_v, 1'b1, 1'b1, fl_d, fl_i,
  fl_z, fl_c}` hardcodes bit4 (and bit7) to 1 — that is the constant B=1 in
  its trace. Interrupt pushes use a separate composition with B cleared
  (`int_active`), and `do_writeback(R_P)` restores only N,V,D,I,Z,C — B
  discarded, same as G.

Both cores therefore push **identical bytes in all four scenarios** (PHP→B=1,
BRK→B=1, IRQ/NMI→B=0) and discard B on restore; they merely display the
undriven bit oppositely (0 vs 1). This is consistent with the r65c02
harness, which already skips `P_B` in its equivalence gate ("never driven in
VHDL").

### 4.5 Apparent differences that were ruled out

- SP after PHA `$05A9`, Z after TSB `$0640`, N/C after ASL/ROL.zx `$065E`–
  `$0660`, I at IRQ entry: all ±1-row state-update skew (Step 4), not real.
- DO mismatches on read rows and the RW-only flip rows: sampling artifacts
  (Section 3).

## 5. Interpretation and decision point

N was deliberately built to **W65C02S datasheet** cycle counts (file header;
PLAN_gameKing_core_20260731.md decision 1). G is the FPGA64/R65Cx2 lineage,
whose timing matches real silicon only incidentally. The four-opcode delta
is therefore an expected model difference, not a bug in N — with one nuance:
on JMP (abs,X), **G** is the one deviating from both real chips (5 vs 6).

Options:

1. **Keep N as-is (recommended).** Document the four-opcode timing delta as
   a known model difference; keep the equivalence gate on instruction stream,
   memory transactions/final state, interrupt behavior, and end-state
   registers — all of which pass. This preserves N's W65C02S fidelity; G's
   extra old-value write-back on `.ax` shifts matches no real silicon.
2. **Force cycle-exact parity with G.** N would need: +1 cycle writing the
   old value on shift/rotate abs,X, −1 internal cycle on JMP (indirect), −1
   indexing cycle on JMP (abs,X). This makes N *less* datasheet-accurate to
   match FPGA64 quirks, and is only worth it if some downstream test requires
   G-exact cycle timing.

## 6. Reproduction

Generate the traces (from `Apple-II-Verilog_MiSTer`, per the runner header):

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File module_tests/cpu_65c02/run_divergence.ps1
# or, against existing traces only:
.\module_tests\cpu_65c02\run_divergence.ps1 -CompareOnly
```

Analysis scripts (this document's numbers):

- `module_tests/cpu_65c02/build/cycle_diff.py` — Step 3: per-opcode/mode
  cycle-length census, G vs N, with first-instance locations.
- `module_tests/cpu_65c02/build/final_check.py` — Step 5: final-memory
  reconstruction + diff; NMI-region row dump.
- `module_tests/cpu_65c02/build/inspect_insn.py [insn# ...]` — Step 4: raw
  row dump of aligned instruction *i* (and its neighbors) from both traces.
- `module_tests/cpu_65c02/analyze_traces.py` — earlier event-aligned /
  cross-correlation pass (fetch events, register-sequence shifts) covering
  both the r65 and t65 pairs.

Run with `/c/msys64/ucrt64/bin/python3` from the repo root.
