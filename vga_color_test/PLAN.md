# Standalone VGA Color Tester Plan

## Goal

Build a small, independent Verilator application under
`Apple-II-Verilog_MiSTer/vga_color_test/` for rapid development of the active
Verilog VGA controller. The tester will load 1-bit Apple II images, feed their
video bits and timing signals directly into the controller, and display the
processed RGB output in an ImGui window.

The application must retain the existing video zoom control while omitting all
unrelated machine, audio, disk, keyboard, memory, and debug panels.

## DUT Contract

Instantiate only `vga_controller` through `vga_color_test_top.sv`.

Inputs to drive:

- `CLK_14M`: one complete rising/falling clock cycle per source sample.
- `VIDEO`: one Apple II monochrome video bit per 14 MHz clock.
- `COLOR_LINE`: whether the current source line permits artifact color.
- `SCREEN_MODE[1:0]`: Color, B&W, Green, or Amber.
- `COLOR_PALETTE[1:0]`: NTSC //e, IIgs, AppleWin, or Custom.
- `GRAY_SEAM_FIX`: current "Sharper RGB" option.
- `NTSC_VERTICAL_COMB`: current vertical-blend option.
- `HBL` and `VBL`: source blanking generated by the harness.
- `ioctl_*`: held inactive initially, but retained so custom palette loading can
  be added without changing the wrapper interface.

**Decision Q2 (2026-08-30) - COLOR_LINE control.** Polarity verified in the
DUT (`if (!COLOR_LINE)` is the mono path) and in the core
(`GR1 <= not (TEXT_MODE or (V2 and V4 and MIXED_MODE))` - text mode is all
mono, plain LORES/HGR is all color). Replace the single checkbox with a
3-position combo plus a boundary-line slider:

| Position | COLOR_LINE per source line | Meaning |
|----------|---------------------------|---------|
| No color | 0 on all lines | monochrome everywhere |
| Text + graphics | 0 for lines < N, 1 for lines >= N (N adjustable 0..191, default 1) | "active after one specific line" - e.g. mono text header over color graphics |
| Full color | 1 on all lines | HGR / DHGR |

The boundary N is a small slider shown only in the Text + graphics position.

Outputs to capture:

- `VGA_R`, `VGA_G`, and `VGA_B`.
- `VGA_HBL` and `VGA_VBL` for valid-pixel qualification.
- `VGA_HS` and `VGA_VS` for timing diagnostics.
- `ioctl_wait` for future custom-palette support.

The module has no reset port. On application startup, image changes, or the
manual Reset button, reconstruct the Verilated model and run a deterministic
preamble (two full 262-line frames, discarded). This prevents stale
vertical-comb history from affecting a newly selected image. Mode toggles
(display, palette, seam, comb, COLOR_LINE) change DUT inputs live with no
reconstruction - that is the intended on-the-fly behavior (Decision Q3).

## Source Timing Generator

**Decision Q3 (2026-08-30) - full NTSC frame, continuous live display.**
Simulate the complete 262-line NTSC frame: 70 VBL lines followed by 192
active lines, repeated forever. The DUT's `VGA_VS` pulses at vcount 33-35
(`VBL_TO_VSYNC=33`, `VGA_VSYNC_LINES=3`), which the 70-line blanking covers.

The application runs a **continuous simulation loop**: the selected image is
re-fed every frame and the GUI shows the live result, so display/palette/seam/
comb/COLOR_LINE toggles take effect on the fly (within one line) without any
rebuild. Model reconstruction + preamble happens only on image change and on
the manual Reset button (see DUT Contract), never on mode toggles.

Use the timing contract already exercised by
`../module_tests/vga_controller/vga_controller_verilog_tb.sv`:

- 912 source clocks per line.
- `HBL=1` for clocks 0 through 351.
- `HBL=0` for clocks 352 through 911.
- The controller consumes 560 active samples after the falling edge of `HBL`.
- 192 active image lines per frame, 560 source samples each.
- Frame = 70 VBL + 192 active = 262 lines = 238,944 source clocks.

The harness should maintain source line/clock counters and update inputs before
the DUT rising edge. Sample outputs after the rising edge, matching the existing
module-test convention.

Capture output pixels only when both `VGA_HBL=0` and `VGA_VBL=0`. Do not encode
the controller pipeline delay as a magic constant; let output blanking qualify
the valid RGB samples.

## Input Image Handling

Use a small image loader such as `stb_image.h`. Convert every loaded image to a
monochrome bit using a configurable luminance threshold, defaulting to 128.
Ignore RGB color in the source image after thresholding.

Support these explicit input profiles:

| Input size | Mapping to the 560 active source samples |
|------------|------------------------------------------|
| 280x192 | Duplicate each source pixel horizontally |
| 284x192 | Crop two source pixels from each side, then duplicate |
| 560x192 | Feed directly |
| 568x192 | Crop four samples from each side |

Reject unsupported dimensions with a visible error instead of silently
rescaling. Keep cropping code isolated in `image_source.cpp` so it can be
adjusted after visual comparison with the existing captures.

Copy these initial 284x192 source images from `../../apple2ntsc/python/`:

- `monochrome_input.png`
- `arena.png`
- `robocop.png`
- `total_replay.png`

The 568x192 files under `../../apple2ntsc/screens/` and
`../../apple2ntsc/apple2_palgen/preview_images/` are processed/reference images,
not the primary source-bit inputs. They can be used later for visual comparison.

## GUI

Create one compact controls window and one video window.

Controls:

- Image dropdown populated from bundled `assets/` files.
- Open-image button for an arbitrary PNG or BMP.
- Luminance-threshold slider.
- Display combo: Color, B&W, Green, Amber.
- Palette combo: NTSC //e, IIgs, AppleWin, Custom.
- Artifact rendering selector: Composite or Sharper RGB.
- NTSC vertical blend checkbox.
- COLOR_LINE combo (No color / Text + graphics / Full color - Decision Q2)
  plus a "color starts at line N" slider (0..191, default 1) shown for the
  Text + graphics position.
- Reload/reset button (reconstructs the DUT model + preamble).
- **Save-frame-as-PNG button** (user request 2026-08-30): dumps the current
  captured 559x192 RGB frame to a PNG file (file dialog or fixed name with
  timestamp). Reuses the same PPM/PNG encoder path as `--dump-frame` so the
  GUI screenshot and the headless dump are byte-identical for the same frame.
- Status text showing input dimensions, captured dimensions, frame count, and
  any load or timing error.

Video window:

- Existing ImGui zoom slider behavior.
- Optional rotate and vertical-flip controls retained from the full harness.
- Processed DUT output texture.
- A small monochrome input preview if it does not complicate the first working
  increment.

Do not include the audio panel, simulation stepping controls, memory editor,
disk controls, virtual keyboard controls, or debug console.

The control mapping should be direct:

```text
Display                  -> SCREEN_MODE
Palette                  -> COLOR_PALETTE
Composite/Sharper RGB    -> GRAY_SEAM_FIX
NTSC vertical blend      -> NTSC_VERTICAL_COMB
COLOR_LINE combo + N     -> COLOR_LINE (per-line, Decision Q2)
```

## Rendering

Start from the existing `../verilator/sim/sim_video.cpp` and `.h` code, but copy
only the SDL/OpenGL/ImGui texture behavior needed by this tester. Remove audio,
input-controller, bus, storage, and full-machine dependencies.

Use a fixed 560x192 RGB framebuffer for the processed image. Upload it to the
texture once a complete frame has been captured. The GUI may scale the texture,
but the simulation framebuffer must remain pixel-exact.

## Implementation Order

### Phase 1: Headless DUT and feeder

1. Create the folder, copied controller, minimal wrapper, Makefile, and Windows
   build/run scripts.
2. Implement deterministic clock, horizontal blanking, and vertical blanking.
3. Generate a synthetic bit pattern without any GUI or image loader.
4. Capture one exact 560x192 frame from qualified DUT output.
5. Dump the result as PPM and inspect it.

First discriminating check: the output must contain exactly 107,520 valid
pixels, with 560 pixels on each of 192 lines.

### Phase 2: Image source

1. Add image loading and luminance thresholding.
2. Implement the four supported dimension profiles.
3. Add the bundled 284x192 examples.
4. Confirm that 284x192 input produces 560x192 DUT output without shifting
   line boundaries.

First discriminating check: B&W mode must produce only pixels where `R=G=B`.

### Phase 3: ImGui application

1. Add the minimal SDL/OpenGL/ImGui shell.
2. Add the output texture and zoom control.
3. Add image selection and display controls.
4. Reconstruct and re-prime the DUT whenever image or processing settings
   change.
5. Add visible status/error reporting.

First discriminating check: changing each control must alter only its matching
DUT input and produce a stable complete frame.

### Phase 4: Automated validation

1. Add `--smoke-test` without GUI initialization.
2. Load every bundled image.
3. Exercise all four display modes and the three built-in palettes.
4. Exercise Composite/Sharper RGB and vertical blend off/on.
5. Verify deterministic frame hashes across two clean DUT reconstructions.
6. Verify unsupported image dimensions fail cleanly.
7. Add optional PPM output for failed cases.

## Acceptance Criteria

- The tester builds independently of the full Apple II simulator.
- Only the VGA controller and its tiny wrapper are Verilated.
- All bundled 1-bit images appear in the dropdown and render successfully.
- Output capture is exactly 560x192 with no missing or extra line pixels.
- Color, B&W, Green, and Amber modes are selectable.
- Composite/Sharper RGB and NTSC vertical blend are independently selectable.
- Zoom works as in the existing ImGui simulator.
- No audio panel or audio dependency is present.
- Image or mode changes cannot retain stale vertical-comb history.
- `--smoke-test` runs without opening a window and exits nonzero on failure.
- The Save-frame-as-PNG button writes a valid PNG of the current frame.
- Verilator lint introduces no unexplained correctness warnings.
- README documents build, run, image requirements, controls, and the explicit
  copied-controller synchronization workflow.

## Known Risks

- The controller has no reset, so deterministic model reconstruction and
  blanking preamble are required.
- The vertical comb stores one prior RGB line; live setting changes without
  reinitialization can produce misleading transient output.
- The controller's active output is 560 pixels even though several historical
  captures are 568 pixels. Keep cropping explicit and testable.
- Custom palette download uses a four-beat protocol and has historically been
  sensitive to assignment timing. Defer GUI palette editing until the basic
  tester is stable.
- The copied controller can drift from the active source. Never assume parity;
  compare explicitly before transferring a change.
- Verilator proves simulated logic behavior, not Quartus timing, memory
  inference, or final hardware image quality.
